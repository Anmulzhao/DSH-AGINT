# 三态核账：代码态 / 运行态 / 数据态

2026-10-03 一天之内，进化主链（1a 预测锁定、1b R1′ 实测尺、R2 技能金标、Ledger 锚定）
四次踩在同一件事上：**改完了 ≠ 加载了 ≠ 有数据**。三次是靠实测发现的，一次是靠
读自己的旧文档发现的（那份文档已经写谎了）。

配套阅读：`measure-before-quota`（尺子准不准）、`check-soundness`（秤坏没坏）。
本篇管的是**这三句话各自什么时候才允许说出口**。

---

## 一、三个态与各自的判据

| 态 | 成立的判据 | 一条可复现的命令 | ⛔ 不能拿来冒充的邻态 |
|---|---|---|---|
| **代码态** | 仓库工作树里有实现，且有测试绑定它 | `git log --oneline -3` + 跑该插件测试套件 | 不证明运行态 |
| **运行态** | 部署位文件是新的 **且** 进程读的是新的 | 槽文件 mtime 早于进程启动时刻（见 §3） | 不证明数据态 |
| **数据态** | 生产存储里有真实行，且来源是真实事件 | 读 `~/.dsh/storages/agint_*.json` 的表（见 §4） | 只能反推前两个态中较旧的那个 |

1. 说「已完成」之前，先答是哪一态。答不出 ⇒ 不许说。
2. 汇报时三态分栏写。混在一栏里，读者会自动把代码态读成运行态。
3. 部署之后重测数据态，不要用部署前的读数。**旧读数既不能证明「已修」，也不能证明「仍坏」**（实测：`ledger-anchor` 最近一次失败发生在部署带该能力的 memory 之前）。

## 二、「有函数没 caller」等于机制不存在

代码态的判据不是"文件在"，是**有人调它**。

- 实测案例：`verifyHypothesisLock` 有函数、有单测、全仓零调用方 ⇒ 那把锁实际只防得住
  "改 predictedDelta 数值"，防不住改 targetMetric、改 changedPlugins、删 `contract_locks` 行。
  补上调用点（driver 0.2.16 的 `lib/contract-audit.js` 三向清点）才算存在。
- 同构案例：baseline 回归 job 每周期写占位行 `passRate:1.0 / passed:0 / total:0`，
  因为真 runner 从未被注入。**一个周期性写数的 job 比一个不写的 job 更危险**——它会喂给下游一个假的健康值。
- 验收口径：**这条机制被绕开时，有没有一条测试会红？** 没有 ⇒ 它没接线。

## 三、运行态只认物理顺序，不认版本号

1. 本项目两处运行槽：`~/.dsh/.agint-bundle/plugins/`、`~/.dsh/profiles/web/plugins/`。**两槽都要改**，漏一处 = 静默分叉。
2. 版本号会骗人（工作树 bump 了但没 cp）。可信证据是顺序：**槽文件 mtime 早于进程启动时刻** ⇒ 该进程读的是新文件。
3. 三条口径一起取，缺一就不算确认：① 槽 `package.json` 的 version；② `lastBootAt` 与 pid；③ 启动块日志有无 `did not activate` / 新增 ERROR。
4. ⚠️ 别只信 `marker.json` 里的 pid。实测出现过 marker pid 与端口持有者 pid 不一致。以**进程启动时刻**为准更硬。
5. 部署位探针脚本要**只读**、可重跑、断言的是行为不是文件内容（先例见 §9 的红绿自证）。
6. 加插件/改挂载会触发全站重启，不要塞进一次小改动里。

## 四、数据态要读活的存储

1. 生产 JSON 是整单元形状：`{unit, global, tables:{表名:{主键:值}}}`。**数行要 `Object.keys(u.tables[t]).length`**，不是 `rows.length`。
2. 新表可能压根不存在 ⇒ 宿主补空 Map。"表不存在"与"表里 0 行"是两句话，别说成一句。
3. cron 状态在 `agint_cron.json` 的 `tables.cron_state`，**它是以 job id 为键的字典**，不是数组。
4. **`lastRunAt` 一律是 UTC**（结尾 `Z`）。先换时区再下"上次什么时候跑的"的结论，否则会把上午的失败读成凌晨的。
5. 一次真实读数：`outcome-measure` 跑完 `scanned:6`、`counts:{}`，`measurable` 就是 0——**这不是故障，是链上 6 条全是重建条目、`references.preimagePath` 为空 ⇒ 基线态取不到 ⇒ 永久不可测**。测不到要如实报"0 条可测 + 原因"，不许报"没有改进"。
6. 读活的存储之前先确认它没被并发改写（见 §8）。

## 五、判据要外置，而且写在数据里不写在散文里

「裁判不能是选手」这条纪律，只有在**代码读得到**的时候才成立。

- 落地形状：case 存 `eval/skills/<preset>/<skill>.cases.json`，与被改的 `presets/agint/skills/<skill>/SKILL.md` **不同池**；
  只有 `addedBy:'boss'` + UTC 毫秒 `approvedAt` 的条目进分母；我生成的一律 `addedBy:'agent'` ⇒ 一条都不算数。
- 红绿自证：把签核门临时改成 `const signed = true` ⇒ 5 条测试立即变红（含端到端）。**放宽后不红的测试等于没测。**
- 双刃：标签住在仓库、运行槽里没有 `eval/` ⇒ **改标签不需要部署也不需要重启**（数据态当场变）。这条要主动说明，否则别人会以为改了标签线上就还是旧的。
- 已签的判据不许为了内容变绿而放宽。实测分叉：某技能 36 条签完后停在 75%，剩 5 处是通用系统路径 ⇒ 保留 75%，不删判据也不删内容（删了就是让指标替内容做主）。

## 六、测不到不是 0 分

1. 覆盖门筛不到测试 ⇒ `NO_EVIDENCE`，**表里一行都不写**。写 0 会被下游读成"改了但没效果"。
2. 0 条已签核 ⇒ `passRate: null` ⇒ 上层 `NO_EVIDENCE`，`reason` 里带"已签核 0 条 / 待签核 N 条"。那句提示是给人看的操作项，不是噪声。
3. 仪器跑不出这个量纲 ⇒ `UNSUPPORTED_METRIC`。⛔ 不许找"看起来像"的代理指标：token 与延迟在当时的生产里根本没有生产者。
4. 死区取 `max(0.5 × τ, 噪声标准差)`。全仓通过率当尺子的话，1/1928 ≈ 0.05pp 会被死区吃掉 ⇒ 有效变异读成"无变化"。

## 七、仪器故障与被测对象不合格，分两个终态

- case 的 kind 不认、正则坏 ⇒ `*_INVALID`；文件读不到、case JSON 坏 ⇒ `*_FAULT`。都与"这条没通过"分开。
- 混起来的后果：一个坏掉的标签文件能把整条链的技能条目全读成回归 ⇒ 一堆假红，且查不到源头。
- 同理：**归因不明要出声**（`CONTRACT_TAMPERED` 必须在起子进程之前拒，文件没换、表里没行）。

## 八、红绿自证脚本自己的坑

1. 从测试里 spawn `node --test` 子进程要**删掉 `NODE_TEST_CONTEXT`**，否则子进程继承父进程的报告模式。
2. 非 TTY 下 `node --test` 会退化成 spec reporter（只打 `✔`，一个 `not ok` 都没有）⇒ 脚本读不到 `# fail` 就误判"没变红"。**一律加 `--test-reporter=tap`**，并且"`# fail`/`# pass` 缺失"要直接抛错说结论不可信，不许当 0 处理。
3. 断言"两次跑逐条一致"要防假基线：裸 `git worktree` 缺 `node_modules` 会让场景数从 123 掉到 23。守卫终态 `NO_TEST_RUNTIME`。
4. 静态模式下输入不存在时必须**显式声明跳过**（记进 `criteriaSkipped`）。静默跳过 = 假防线，会在首跑稳定产出假阳性。

## 九、文档谎报：grep 生成脚本，不 grep 产物

1. 判据：**这个文件是不是生成的？** 看文件头有没有"由 xx 生成"、有没有 `--check` 校验它与源一致。是生成的 ⇒ 改源，不改产物（产物会被下次生成原样覆盖回去，diff 看着对，实际啥也没改）。
2. 实测：规范索引里写着「123 个单元已带 visibility + labelAuthority」，而生成它的脚本里那是一句**硬编码散文**，数据文件里两个字段都没有。
3. 最快探测器：**同一份文档里互相矛盾的两句话**。一句"✅ 完成"、一句"无这两个字段" ⇒ 至少一句是计划语气冒充实况。把矛盾摊开写（错在哪 / 订正后实况 / 一句话结论），⛔ 悄悄改对——那等于消灭证据。
4. **行号会腐坏，最常见的凶手是你自己**：在同一文件里插了几十行代码，规范里引的 `driver.js:2499` 就指到毫不相干的地方。引用要带**代码片段作锚点**，行号只当带日期的辅助；收工前回读一遍自己引用的位置。
5. 新规范登记是**三处联动**：加进 `specs[]`、从 `pendingSpecs[]` 删同 id、`compatibility-matrix.json` 补升级策略。少做一处会被两道门禁各抓一次。

## 十、独立进程不许直写生产存储

宿主把整个 unit 读进内存，每次 put 整体重写文件（last-write-wins）⇒ 仓外脚本写的行会被
宿主下一次写入静默覆盖。正确形状：**表 + 宿主服务方法 + 只读预览脚本**（先例 `bin/anchor-ledger.mjs`）。
数据态要如实写"生产 0 行"。

## 十一、并行会话的三个串行点

多个会话/子代理同时改同一个仓时，**能并行的判据是"碰不碰同一批文件"，不是"逻辑相关不相关"**。

| 串行点 | 原因 | 处理 |
|---|---|---|
| 部署 + 重启窗口 | 两槽共用，全站一个进程；第二次重启打断第一次的验证 | 各线写完，攒成**一次** cp + **一次**重启 + **一次**验证 |
| 同一个 git 工作树 | 树是脏的（别的会话未提交的活）；并发 commit 会把别人的改动卷进来 | 子代理各自 worktree；commit 只点名自己改的文件（⛔ `git add -A`）|
| 共享文件 | 典型：`plugins/agint-cron/lib/jobs.js`（任何加 cron job 的线都改它）、规范索引与其生成脚本 | 开工先声明文件面；撞车的项排队，不并行 |

- 声明"这条线不碰任何共享文件"要能被 `git status` 核到。
- 别的会话的脏文件**不要当基线读**（它的形状可能正被改），也不要动。

## 十二、收尾自检（八问）

1. 我说的是哪一态？另一态有人替我脑补了吗？
2. 新机制的调用点在哪？把它绕开会不会有测试红？
3. 两槽都改了吗？槽 mtime 早于 boot 吗？
4. 生产存储里真有新行吗？读数用的是活的地方吗？
5. 时区换算了吗（UTC → 本地）？
6. 测不到的部分，是写成 `NO_EVIDENCE` 还是被写成了 0？
7. 文档里那句"已完成"，在生成脚本里对得上吗？
8. 待老板点头的动作（部署 / 重启 / push）是不是被我顺手做了？

一句诚实话：**三态分开报会让进度看起来比实际慢。** 这是这条技能存在的全部理由。
