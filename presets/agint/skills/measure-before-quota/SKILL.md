# 造尺子：度量口径、门禁校准与豁免治理

2026-10-02 Phase-0 Sprint 18 的六次失误。五次发生在「开始造之前」——
**分母没定义、历史数字没溯源、粒度没对齐执行器、存量没清零、豁免没上锁。**

配套阅读：`check-soundness`（校验器**自身**的失效模式：静默降级、判据含噪、
机器私有事实进库）。本篇管的是**尺子准不准**；那篇管的是**秤有没有坏**。两者都要过。

---

## 一、分母先于比率

设计文档写「从 **104 个**场景中分配 60/32/12」。核对仓库，「场景」至少指三样东西：

| 候选单位 | 数量 | 为什么不是它 |
|---|---|---|
| `.scenario.json` **文件数** | 37 | 一个文件可以是数组，含多个独立单元 |
| `driver.js` 全量回归的**单元数** | **123** | ← 采用这个 |
| 单测**断言数** | 216+ | 那是插件自身单测，不是被评估对象 |

差异来源是实测的，不是推的：

```javascript
// eval/scenarios/driver.js 的 loadScenarios
const items = Array.isArray(parsed) ? parsed : [parsed];
for (const item of items) out.push({ file: f, scenario: substituteRoot(item) });
```

`agint-diagnosis.scenario.json` 一个文件 10 个单元，`agint-cron.scenario.json` 2 个。

> **规则**：设计文档里的**数字**和**名称**一样需要独立验证。名字可以靠上下文猜，
> 数字猜错直接污染下游所有决策。
>
> 自检问句：*准备说「X 占 Y 的 Z%」时，Y 的分母是怎么数出来的、代码在哪一行？*
> 答不上来 ⇒ 这个百分比不许进交付物。

**产出的东西要能回答「口径边界」**：把计量范围写进机器可读的字段
（本项目写在 `inventory.json` 的 `unitScope`），不是只写在文档里——
文档没人 grep得到，字段会被人读。

## 二、历史数字有两种读法

「文档说 92/104，实测 123，差 +19。」直觉是「门禁跟文档对不上，让它们一致」——
于是想把 123 改回 104，或把文档改成 123。**两种都错。**

git 逐级实测出的演变链：

| 时点 | 事件 | 单元数 |
|---|---|---|
| 2026-08-28 | 基线 | 104 |
| 08-29 | 新增 event-bus s12 | 110（+6） |
| 09-03 | self-model(10) + deploy-budget(5) | 125（+15） |
| 09-09 | 两个文件移入 `dedicated/` | 125（数不变，但 driver 不再扫到） |
| **实测日** | **driver 实跑** | **123** |

**92/104 在 2026-08-28 那个时点完全准确。** 错的不是数字，是 09-09 之后文档没更新
——这是**文档的债，不是门禁的 bug**。

> **规则**：看到「文档说 X、实测 Y」，第三种可能性必须先排除：
> **X 在它自己的时点是对的**。
>
> 固定查法：`git log --follow <file>`，在关键提交上 `git show <sha>:<file> | <计数器>`，
> 把数字的**时间序列**拉出来。拉不出序列，就没资格说哪个对。
>
> 同理，「fail 从 12 降到 5」不能停在「部分已修复」——那是不及格的严谨度，
> 因为它让下游配额的对象不明。**差集必须逐项列出去了哪。**

## 三、粒度对齐执行器，不对齐文件

Inventory 第一版把某个子目录记成「2 个单元」——因为我用**文件枚举**做单位。
但它有自己的 runner：

| runner | 它自己的取数 | 单元数 |
|---|---|---|
| `run-mutator-eval.mjs` | `parsed.scenarios` | **19** |
| `run-counterfactual-stress.mjs` | `parsed.fixtures` | **10** |
| | 合计 | **29** |

于是「它有几个」从 2 变成 29，而这个数直接决定口径边界。

> **规则**：**执行单元的粒度由消费它的执行器定义，不由存储它的文件定义。**
> 问「执行器自己怎么数」，不要数文件。
> 同理：driver 扫哪些文件以 driver 的 `readdir` 为准（只扫 `__dirname`、不递归），
> 不以目录树里存在什么为准。

## 四、分母纯净度：状态未知就别混进去

那 29 个单元在主口径下的 `lastKnownStatus` 是 `UNKNOWN`——**没被执行过**，
不是通过也不是失败。

若按「总数 152」写通过率，得到 `118/152 = 77.6%`。这个数看起来正常，
实际把 29 个未知当成了 29 个非通过。**它比 78% 本身更有害**——
因为它让「这批到底跑没跑过」这个问题永远消失在报表里。

| 口径 | 数值 | 有效性 |
|---|---|---|
| driver 口径 | **123** | ✅ 状态全已知，118/123 可计算 |
| 按 runner 粒度并入 | 152 | ❌ 含 29 个 UNKNOWN，通过率不可计算 |
| 按 driver 历史口径 | 125 | ⚠️ 数字没错，但**是另一个口径**，不可与 123 混用 |

> **规则**：分母里只放**状态已知的项**。`UNKNOWN` 不是 0 也不是 1，
> 它是「没测过」，混进任何比率都是造假。
>
> 配套：**写死反转条件**（runner 退役 → 并入 → **重跑全部配额计算**），
> 免得后人当成未完成事项反复提起。

## 五、门禁的第一天必须能过

新校验器写完实测：version 漂移 **14** 处、声明文件缺失 **8** 处、strict 下 **25** 处 backlog。
按「不一致就是错」的直觉全判 ERROR，这道门禁**上线当天就红**。

红灯门禁只有两种结局：被人加 `--no-verify` 跳过，或被人往白名单塞条目直到失去制衡。
**两种都比没有这道门禁更糟。**

| 判据 | 级别 | 本轮实例 |
|---|---|---|
| 破坏性的（导致运行时不正确） | **ERROR** | `name`/`main` 错、manifest 缺失 |
| 权威源尚未定义的（没有唯一真相可比） | **WARN** | version 漂移、声明文件缺失 |
| 门禁自身实现的问题 | **先修门禁** | 比对字段用错 |

**升级 ERROR 的前置条件是这一类已清零。** 清零前升级 = 制造新红灯。

### 误报比漏报更该先修

旧实现对 `plugins/*` 做目录 glob，凡无 manifest 一律报警。实测 3 处**全是误报**：
一个目录是嵌套父容器（patch 挂的是它的子模块），另两个在 patch 里根本没挂载。

修法：**集合来源从目录 glob 改为真实声明反查**（读 `cordis.patch.yml` 的
`name: ./plugins/...` 行），正则**锚定行首**——patch 里有被注释掉的条目，
不锚定会多算。

> **规则**：门禁报的每条异常，先问「**这条是真的吗**」，再问「**怎么修**」。
> 误报清零之前不要谈严格化。
> 并且**未挂载的目录记为 notes，不静默吞掉**——静默吞掉和误报一样有害，只是方向相反。

### 存量未清零的诚实写法

零依赖门禁必须有白名单（zod 由 install.sh bootstrap、react 在浏览器模块表、
`@deepseek-ai/*` 宿主提供）。白名单**checked-in**，逐条写 `reason`。
通用包名豁免还要带 `evidence` 数组 + `providedBy`（指向宿主），否则等于给「随手塞包」开口子。

## 六、豁免是后门，得上三道锁

某插件的 `tests.entry` 指向不存在的文件。选项：(a) 编个空文件骗过门禁；
(b) 删声明；(c) 豁免。

选 (b) 对——**声明一个不存在的入口，比不声明更糟**，它让「有 smoke 门禁」变成假的。
但删完就完事，等于让「这个插件没有测试」这个事实**静默消失**。

⇒ `docs/manifest-declared-file-exemptions.json` 三条硬约束：

1. 每条必须 `reason`（为什么没有）+ `reversal`（什么条件下恢复）——
   **没有 reason 的条目就是后门**
2. **限定豁免字段**（本项目只豁免 `tests.entry`）。README/CHANGELOG 缺失一律补文档，
   不接受豁免——文档可以如实写出来，不存在编造问题；测试入口指向不存在的文件是欺骗
3. **反向冲突检查**：豁免登记了、但文件真实存在 ⇒ 报 `EXEMPTION_CONFLICT`

> **规则**：**豁免不是「承认现状」，是「把现状写下来并留反转条件」**。
> 没有 reason、没有 reversal、没有反向检查的豁免条目，
> 效果等同于把门禁删掉。

## 七、配套的变更纪律

- **rebase / pull 之后必须重跑全量回归**。本次即靠它逮到远程新引入的第三方依赖
  （`check-preset-parity.mjs` 用了宿主提供的 `yaml`），本地零依赖门禁立刻转红。
  push 前不回归 = 把红灯推上去。
- **push 被拒 ≠ 强推**。先 `fetch` + 比两侧文件交集，为空才 rebase。
- **测试要钉返回值，不是钉记忆**。本轮 `classify()` 实际返回 `ALLOWLISTED`
  而非我以为的 `ALLOWED`，第一版断言写错，自测当场抓到。
- **新增豁免/白名单的代价是制衡测试会红**。正确处置是**升级治理**
  （加证据字段 + 加新测试），不是删测试或改断言方向。

造完尺子、门禁上线前逐条过：

- [ ] 我引用的历史数字，拉得出时间序列吗？（拉不出 = 没资格说它错）
- [ ] 计量粒度是消费它的执行器定的，还是我数文件定的？
- [ ] 分母里每一项状态都已知吗？没有 UNKNOWN 混进去？
- [ ] 口径边界写进机器可读字段了吗？反转条件写了吗？
- [ ] 门禁上线第一天，全仓库能过吗？（不能过 = 会被绕过）
- [ ] 门禁升级 ERROR 前，这一类清零了吗？
- [ ] 门禁报的每条异常，我确认过是真的吗？误报清零了吗？
- [ ] 未挂载/不校验的项，是记为 notes 还是静默吞掉了？
- [ ] 我加的每个豁免，有没有 reason、reversal、反向冲突检查？
