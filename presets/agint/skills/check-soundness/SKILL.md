# 校验器自身的可靠性

2026-10-01 一个下午，四次踩坑全是同一类：**检查器出错了，但报出来的还是「通过」**。

## 一、基线取不到 ≠ 这次没查

```js
// ❌ 2026-10-01 实写版本
const live = readLiveTarget(profile);
if (live) targets.push(live);          // 取不到就跳过
// 结果：门禁少查了整条 live 基线，输出照常 exit 0
```

**为什么致命**：输出里那行 `基线 live` 消失了，人只看「✅ 通过」和退出码 0。
一个静默少查一半的检查器，比没有检查器更危险——它把「查过了，没问题」这句话
廉价地卖了出去，而这个「没问题」没有任何依据。

**正确写法**：取不到基线是**被检对象不合格**，不是被检对象没问题。

```js
if (live?.error) {
  baselineFailures.push({ level: 'critical', kind: 'baseline-unavailable', ... });
} else if (live) targets.push(live);
```

**自检问句**：*如果这个输入源整个消失，我的脚本会报红吗？* 不报红就是有洞。
故障注入验一遍：把输入源从环境里摘掉，确认退出码从 0 变 1。

## 二、判据里不能混入「每次都会变」的量

本机快照块带分钟级时间戳，比对时把它算进漂移 ⇒ **每次运行都必然 STALE**，
门禁彻底沦为噪声。症状很隐蔽：`--check` 明明刚跑过，隔几秒又红了。

```js
const VOLATILE = /^> 本机探测时间：.*$/m;
const stripVolatile = (s) => s.replace(VOLATILE, '');
existing !== null && stripVolatile(existing) === stripVolatile(block)
```

时间戳仍写进文件（它是「这条快照什么时候写的」的留痕，有价值），只是不参与判定。

**判据只回答真正的问题**：状态变了吗。其余（时间、随机数、顺序无关的集合）一律排除。

## 三、机器私有事实不能进共享提交的文件

自动块原先把 9 行写进 `AGENTS.md`（两台机器共享提交），其中 6 行机器私有：
`DSH_HOME` 绝对路径、host 插件版本、cron tick、仓库↔host 同步状态。

后果不是「过期」而是 **outright 错误**：Windows 机器提交后，Linux 机器读到的
AGENTS.md 声称自己的 `DSH_HOME` 是 `C:\Users\Administrator\.dsh`。
谁最后跑，谁的机器就是仓库事实。

按「**谁来决定这个值**」拆：

| 归属 | 落点 | 判据 |
|---|---|---|
| 仓库级 | 入库的文档 | **只从仓库读**，不碰本机部署位 |
| 本机级 | `.gitignore` 的文件 | 允许含绝对路径，它永远不被另一台机器读到 |

关键不是搬文件，是**换了数据源**：仓库级事实改成只读仓库侧。
读部署位的话，A 机器装过什么就决定仓库写什么，B 机器跑一次就改回去，来回打架。

**验收方法**（很便宜，值得每次都做）：

```sh
DSH_HOME='/假路径' node 生成器 && git diff --stat   # 期望：入库文件零变化
```

## 四、生成物不该是「另一份真相」

若入库块与本机块都从同一个 host 部署位取值，等于给同一事实建了两个可漂移的副本。
判据：**同一事实只允许有一个权威来源**；展示可以多份，取值只能一份。

## 五、否定断言与假警报

两次同款失误，都出在 grep 上：

1. `grep -c "^- id: "` 返回 0 → 我据此说「该文件没有顶层行」。
   实际是**行有缩进**，模式写错了。正确模式 `grep -cE '[[:space:]]*- id: '` 命中 **45**。
2. `grep preset-agint` 命中 0 → 我据此报「智进 preset 根本没声明，挂了」。
   实际声明行 Loader id 是 `agint-preset`、`config.id` 才是 `agint`——
   命名方向与 shipped 的 `preset-standard`（`config.id: standard`）**相反**。四处都在。

**规约**：

- 否定结论必须带取证痕迹（命中 N 行 / 命中 0 行 / 实际输出）。没有痕迹就写
  「我还没验证」，不要写「它不存在」——两者证据强度天差地别。
- 全称量化（「所有行」「全部字段」）要给出分母。
- **报故障前先证伪自己的探针**：grep 模式写错时的表现，和东西真没了完全一样。
  至少换一种写法复核一次（换个模式 / 直接读文件 / 看上下文）。

## 六、验收的证据分级

从弱到强，报告时说清用的是哪一级：

| 级别 | 手段 | 能证明什么 |
|---|---|---|
| 1 磁盘 | 文件里有新代码 | 什么都没证明——文件早就有了 |
| 2 启动 | 进程启动时刻晚于写入、启动期产物重生 | 宿主**可能**读了新文件 |
| 3 组合 | `dsh --profile <p> --dump-config` 含新行 | 组合**算出来**含新行 |
| 4 活体 | 对**活着的**宿主调 inspect（Tool/Config/Service） | 真的加载了、真的注册了 |

2026-10-01 那次同步的闭环靠的是第 4 级：新 cron job `memory-provider-health`
在重启后**自己跑了一次**（19 → 20 个 job），比任何静态检查都硬。

**知道自己验不到哪一级，并说出来。** preset 平面的工具只对跑在该 preset 上的会话
暴露——不在那个 preset 上时，`Tool.listTools` 查不到它们是**预期**，不是故障。
这时唯一诚实的说法是「我还没法从本会话验证，需要开一个该 preset 的会话」。

## 七、跨机器的字节级坑

- **行尾**：写盘固定 LF；比对前 `replace(/\r\n/g, '\n')`。否则 Windows 编辑器转过
  行尾后 `--check` 每次都误报。
- **执行器**：`execFileSync` 和 `execSync` 是两个导出，少导入一个会在**运行时**
  才炸，而 `node --check` 这种语法检查抓不到。改完实跑一次。
- **时区**：跨机器日志时间戳统一走 UTC 展示，别用本地时区拼字符串。

## 自查清单

写完 / 改完一个检查器，逐条过：

- [ ] 输入源整个消失时，退出码会变吗？（故障注入实测，不是推理）
- [ ] 判据里有没有「每次运行都变」的量？
- [ ] 输出里每个数字都能追到来源吗？
- [ ] 同一事实只有一个权威来源？
- [ ] 跨机器产出一致吗？（换个 env 跑一遍 diff）
- [ ] 改完**实跑**过，不是只过语法检查？
- [ ] 报结论时带取证痕迹，分母齐全？
