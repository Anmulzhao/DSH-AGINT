# 哲学锚点工程化检查项 · Philosophy Checkpoints

> 把 `PHILOSOPHY.md` 的五大哲学对照转化为**可验证的检查项**。
>
> **核心原则**：哲学不是装饰，是每个 P 阶段验收的硬性 checklist。
>
> **本文与 `路线图` 节奏章节呼应**——每个 P 阶段提交前必须勾完对应检查项。

---

## 一、为什么需要哲学工程化

`PHILOSOPHY.md` 五大对照是 AGINT 的"宪法层"，但仅靠阅读无法保证落地。
两个常见陷阱：

1. **哲学装饰化**：把哲学挂在 README 顶层，平时不用
2. **哲学侵犯**：用"工程必要性"为借口绕过哲学

工程化检查项 = 强制把哲学**变成 checklist**，每次提交前必须勾。

---

## 二、五大对照 → 检查项

### 2.1 简洁 > 冗余

| 检查项 | 验证方式 | 阈值 |
|---|---|---|
| 新增功能不引入新插件架构层 | 审查 PR 描述 | 仅在现有插件化架构内 |
| 单个 plugin 净增代码 ≤ 200 行 | `git diff --stat` | 净增 ≤ 200 行（含测试） |
| 单次提交代码行数 ≤ 500 行 | `git diff --stat` | 变更 ≤ 500 行 |
| 文档更新必附带"删除什么" | 审查 PR 描述 | 新增内容有同等或更多删除 |
| 一句话能说清的不写一段 | 文档长度 | 每个章节 ≤ 50 行 |
| 一个函数能完成的不开第二个 | Code review | 函数复用率 ≥ 80% |

**落地工具**：
- `git diff --stat` 在 CI 中自动检查
- 人工 Code review 强制阅读

### 2.2 真实 > 讨好

| 检查项 | 验证方式 | 阈值 |
|---|---|---|
| 评估报告必须展示原始失败数据 | 审查报告 | 失败案例不能隐藏 |
| HARM 分数不能独立决策 | 审查决策 | 必须与 TRACE-P 联合使用 |
| 不确定就明说"不确定" | Code review / 文档 | 没有模糊表述 |
| 复盘报告不能只列成功 | 审查报告 | 失败:成功 ≥ 1:3 |
| 老板问"做完了吗"时回答"没有"也能过关 | 文化沿袭 | 不可妥协 |

**落地工具**：
- 复盘报告模板强制包含"原始失败数据"章节
- D-QAF 决策必须 `safety + reliability + effectiveness` 三项都列出

### 2.3 靠谱 > 聪明

| 检查项 | 验证方式 | 阈值 |
|---|---|---|
| 行为可预期 > 一次惊艳 | 行为稳定性 | 同一输入 100 次结果一致 |
| 变更可回滚 > 一步到位 | rollback 测试 | 100% 可回滚 |
| 任何修改都经过 D-QAF 评估 | CI | 100% 走流水线 |
| 渐进式发布 > 大爆炸 | 灰度策略 | 严格走 Phase 1→2→3→4 |
| 测试通过率 ≥ 95% | CI | 失败即拒绝合并 |
| 依赖固定版本 | `package.json` | 不允许 `^` 或 `~` |
| 关键路径双写 | Code review | 升级前后可同时跑 |

**落地工具**：
- CI 强制 D-QAF 流水线
- 灰度发布机制（v0.4 落地）

### 2.4 主动 > 被动

| 检查项 | 验证方式 | 阈值 |
|---|---|---|
| 隐患看见就动手 | 复盘报告 | 发现后 24 小时内提 proposal |
| 重复任务第二次就自动化 | 复盘报告 | 第二次出现就触发自动化评估 |
| 退化/停滞自动告警 | `agint-quality-eval` | 检测到立即冻结 |
| 梦境/复盘主动跑 | cron 调度 | 稳定运行 100% |
| 文档主动更新 | 提交验证 | 代码与文档同步 |

**落地工具**：
- 退化/停滞探测器（v0.3 引入）
- 自动化任务清单（`docs/lessons/` 编目）

### 2.5 安全 > 效率

| 检查项 | 验证方式 | 阈值 |
|---|---|---|
| 沙盒前置 | D-QAF 流水线 | Phase 1 必走 |
| 静态扫描前置 | `agint-rules` | 启动时加载 |
| 硬约束清单 | `security-boundary.yaml` | 100% 覆盖 |
| 性能优化必须附带安全分析 | PR 审查 | 必填 |
| 危险操作先列清单等确认 | 老板复盘 | 不可绕过 |
| 自动部署 ≤ 3 次/周 | `agint-quality-policy` | 超限人工审核 |
| L0 变更需要人类多签 | CI | 物理隔离 |
| secrets 走 `$DSH_HOME/secrets/` | 文件扫描 | 不在仓库中 |

**落地工具**：
- `docs/security-boundary.md` 硬约束清单
- `agint-rules` 红线规则
- 人类否决权（dsh approval 机制）

## 四、强制复盘项

每次周复盘（`agint-evolve` 生成 `YYYY-MM-DD.md`）必须包含一个章节：

```markdown
## 哲学对齐检查

- [x] 本周提交 / 部署清单
- [x] 逐项对照五大对照检查项
- [x] 失败项的处理计划
```

不勾完这一章节 = 复盘报告不完整 = 视为未完成。

## 五、违反哲学的处理流程

### 5.1 轻微违反

- Code review 中发现但未合并
- 立即退回修改

### 5.2 中等违反

- 已合并但未部署
- revert 提交 + 写 `docs/lessons/`

### 5.3 严重违反

- 已部署到生产
- 立即冻结 + 启动回滚 + 老板审批
- 写 `agint_evolution/failure-patterns/`
- 复盘必须总结根因

### 5.4 不可妥协

- 篡改 `PHILOSOPHY.md` 五大原则
- 关闭 `agint-rules` 全部 deny 规则
- 删除 `agint_evolution` 演进日志

→ 这些是 `L0_FROZEN_VIOLATION`，详情见 `docs/security-boundary.md` 第四章。

## 七、哲学锚点护栏速查

|---|---|---|

| 真实 > 讨好 | 评估报告不隐藏失败 | 进步假象 |

| 安全 > 效率 | 沙盒前置 | 翻车陷阱 |
