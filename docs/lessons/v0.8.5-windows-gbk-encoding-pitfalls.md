# 经验教训 — v0.8.5 Windows GBK 编码坑（安装/部署/验证链路）

> 写于 2026-09-29。AGINT 在中文 Windows（代码页 936/GBK）上安装、部署、验证时踩过的编码坑合集。
> 与 v0.4（Windows path-escape）、v0.7.1（install bootstrap rescue）同族：**都是 Windows 独有、
> Linux 上永远不会复现、报错信息几乎不指向真凶**的坑。区别在于本篇的坑不抛异常 —— 它们
> **静默污染数据或静默误导判读**，是「装完像没装」类事故的常见底层原因。

## TL;DR

PowerShell 5.1 有**三套互不一致的默认编码**（重定向 UTF-16 / 管道 ANSI(GBK) / `Set-Content -Encoding UTF8` 带 BOM），
dsh 日志按 GBK 写、应用按 UTF-8 读 → 乱码；JSON 带 BOM 会让下游 `JSON.parse` 拒收。
全部坑共享一条元规则：**中文 Windows 上，凡是「写文件」「传中文」「看日志」，一律显式管编码，别信默认值。**

| # | 坑 | 症状 | 铁律 |
|---|---|---|---|
| 1 | dsh-web.log 中文乱码 | 日志里中文全是 `锟斤拷`/`闆跺懡` 类 | 用前后行判义，不逐字读 |
| 2 | PS 5.1 `>` 重定向写 UTF-16 | 下游 Read 报 `binary file` | 重定向改 `| Set-Content -Encoding UTF8`，或干脆用 Git Bash |
| 3 | `Set-Content -Encoding UTF8` 带 BOM | 下游 `JSON.parse` 拒收 `Unexpected token U+FEFF` | 写 JSON 用 `[IO.File]::WriteAllText($p,$json,(New-Object Text.UTF8Encoding($false)))` |
| 4 | PS 管道按 ANSI 解码显示 `闆跺懡涓?` | 误判 commit message 入库即乱码 | 先 `[Console]::OutputEncoding=UTF8` 再复核；git 对象里是好的 |
| 5 | 中文 commit message 走 PS 内联 `-m` | message 编码随 PS 编解码漂移 | Write 成 UTF-8 文件 + `git commit -F <file>` |
| 6 | `execFileSync('powershell',…)` 取中文 | node 拿到的中文是 OEM 代码页乱码 | 别经 PS 转手；直接 node 读源头 |
| 7 | `Out-String` 捕获 node 输出 | 非 ASCII 全乱码，断言抽风 | 测试断言用 ASCII 前缀（`PASS`/`FAIL`/`# tests`） |

## 背景：为什么「安装」环节最先撞上

AGINT 装完不是终点 —— 装后验证要**看日志判 boot 成功**（坑 1）、**重定向 stdout 抓 preset 激活错误**
（坑 2）、**重启链路传 JSON**（坑 3）、**把结果 commit 回仓库**（坑 4/5）、**跑验收脚本断言输出**
（坑 6/7）。安装教程里每一步「验证」，在中文 Windows 上都埋着编码雷。以下按踩到的时间序展开。

## 坑 1 — dsh-web.log 中文乱码

- **现象**：`C:\Users\Administrator\AppData\Local\Temp\dsh-web.log` 里中文段落不可读
  （`锟斤拷`、`闆跺懡` 等典型误读产物）。
- **根因**：日志按系统 OEM 代码页（GBK/936）混写，而按 UTF-8 读（或反之）——两端默认值不一致。
- **处置**：**不逐字读，用前后行判义**。报错行本身的英文部分（stack、模块名、错误类）通常完好，
  前后行的结构足够定位；中文正文当作「这一段有字」的信号用。
- **教训**：别为「修好日志乱码」花时间 —— 日志是判读材料不是交付物，判读策略比转码划算。

## 坑 2 — PowerShell 5.1 的 `>` 重定向写 UTF-16

- **现象**：按 README 排障法跑 `dsh --profile web > boot.log 2>&1`（preset 激活错误**只打 stdout
  不落日志**，必须这么抓），在 PowerShell 里执行后 boot.log 无法被常规工具读取。
- **根因**：PS 5.1 的 `>` 重定向默认编码是 **UTF-16 LE**，不是 UTF-8。下游按 UTF-8 读 →
  `Read` 直接报 `Cannot display content of binary file`。
- **修复**：`cmd /c "dsh --profile web > boot.log 2>&1"`（cmd 的 `>` 是字节流），或 Git Bash 里跑，
  或 PS 里 `dsh --profile web 2>&1 | Out-File -Encoding utf8 boot.log`。
- **实测出处**：2026-09-18，`git … > file` 同款坑先行踩中，机制相同。

## 坑 3 — `-Encoding UTF8` 的 BOM 炸 JSON

- **现象**：agint-restart 链路上，`respawn` 收到重启请求报 `bad request: Unexpected token U+FEFF`，
  请求 JSON 明明肉眼合法。
- **根因**：PS 5.1 的 `Set-Content -Encoding UTF8` **写的是 UTF-8 with BOM**（`EF BB BF`）。
  Node 的 `JSON.parse` 拒绝 BOM 开头的输入。
- **修复**（唯一可靠写法）：

  ```powershell
  [IO.File]::WriteAllText($p, $json, (New-Object Text.UTF8Encoding($false)))  # $false = 无 BOM
  ```

- **佐证**：2026-09-29 `_fix_playbook_fmt_20260929.ps1` 就是这么写的 —— 它还额外做了
  **BOM 感知读入 + 保留原 BOM 状态写回**，说明这条已是本工作区的固化实践。

## 坑 4 — 管道里的「假乱码」：先分清显示层 vs 数据层

- **现象**：PS 里 `git log` 输出中文 message 显示成 `闆跺懡涓?`。
- **错误结论**：「中文 message 入库就坏了」。
- **真相**：git 对象里的字节是**完好的 UTF-8**（node 直读核对过），是 **PS 管道按 ANSI(GBK)
  解码**造成的显示层假象。
- **鉴别法**：先设 `[Console]::OutputEncoding = [Text.Encoding]::UTF8` 再看一遍 —— 变好了就是
  显示问题。**判「数据坏了」之前必须过这一步**，否则会把不存在的 bug 修进 CHANGELOG
  （2026-09-17 真实发生过一次误判并更正）。

## 坑 5 — 中文 commit message 的唯一安全通道

- **规则**：中文 message 一律**先 Write 成 UTF-8 文件，再 `git commit -F <file>`**。
  git 按字节读文件，全程不经 PS 编解码。
- **禁止**：PS 内联字符串传 `-m`（引号嵌套 + 编码双重风险）。
- **复核样板**：`execFileSync('git', [...], { encoding: 'utf8' })` + `writeFileSync(..., 'utf8')`
  再用 Read 看 —— 全程绕开 PS 编解码（`D:/DSH/.tmp/_verify_commit_msg.mjs` 是现成样板）。

## 坑 6 — node 调 PowerShell 取中文必乱

- **现象**：`execFileSync('powershell', [...])` 的 stdout 里中文是乱码。
- **根因**：PS 5.1 对外输出默认走 **OEM 代码页**（中文系统 = 936/GBK），node 按 UTF-8 解 → 乱。
- **修复**：**别经 PS 转手**。要的数据让 node 直接读源头（文件 / 注册表走别的方式 / API）。
  确要经 PS：脚本内首行设 `$OutputEncoding = [Console]::OutputEncoding = [Text.Encoding]::UTF8`
  并实测往返，但这属于「能不用就不用」的通道。

## 坑 7 — 验收断言只用 ASCII 前缀

- **现象**：`Out-String` 捕获 node 测试输出后，中文断言全乱、匹配抽风。
- **修复**：机器判读的标记一律 **ASCII**（`PASS` / `FAIL` / `# tests 106`），中文只给人看。
  本仓库测试输出的 `ok/not ok`（TAP）天然满足。
- **原则**：**凡是给机器判读的通道，从协议上排除非 ASCII**；中文语境的判断交给读报告的人。

## 元规则（为什么坑能排成一串）

| 层 | 默认值 | 谁在用 |
|---|---|---|
| cmd `>` / Git Bash | 字节流 | 安全 |
| PS 5.1 `>` | UTF-16 LE | 重定向 |
| PS 5.1 管道解码 | ANSI / GBK | 显示与捕获 |
| PS 5.1 `-Encoding UTF8` | UTF-8 **with BOM** | 写文件 |
| PS 5.1 对外输出 | OEM（GBK） | 被子进程捕获 |
| Node `JSON.parse` | 拒 BOM | 下游消费 |

六个默认值互不一致，任何两两组合都可能咬人。**元规则：中文 Windows 上，跨进程/跨文件传递
中文或结构化数据时，编码必须由发送方显式声明、接收方显式确认，默认值一律视为不可信。**
