# 经验教训 — 度量口径、门禁校准与豁免治理

> 写于 2026-10-02。Phase-0 Sprint 18（验证体系形式化）全程的六次真实失误。
> 与 `docs/lessons/2026-10-02-preset-codex启用与取证.md` 是**互补的两篇**：
> 那篇讲「取证纪律」，这篇讲「造尺子的人怎么先量自己」。
> 相关技能：`presets/agint/skills/measure-before-quota/`（度量与门禁校准）、
> `presets/agint/skills/check-soundness/`（校验器自身的失效模式）。

## TL;DR

这一轮做的是「给一个系统造度量衡」。真正的教训不是某段代码写错了，而是
**六次失误里有五次发生在「开始造之前」**——分母没定义、历史数字没溯源、粒度没对齐执行器。

| # | 教训 | 实证 | 正确做法 |
|---|---|---|---|
| 1 | **单位未定义前，任何比率都是无效数字** | 设计 v1.0 直接写「104 个场景分 60/32/12」，而仓库里「场景」有三种候选单位（37 文件 / 123 单元 / 216 断言） | 先产出 Inventory 定分母，再谈配额。顺序不可颠倒 |
| 2 | **历史数字不是「当前错误」，是「当时的快照」** | 92/104 差 +19，我一度当成存量 bug 要「修回 104」 | git 逐级实测出 +6→+15 的演变链，确认该时点**确实准确**。数字没错，错的是把它当现状 |
| 3 | 粒度必须**对齐执行器**，不是对齐文件 | dedicated 记成「2 个单元」，实测两个 runner 各有 19 场景 + 10 fixture = **29** | 问「这个执行器自己怎么数」，不数文件 |
| 4 | 状态未知的单元混进分母 = 通过率不可计算 | dedicated 29 单元在 driver 口径下 `lastKnownStatus: UNKNOWN` | 118/123 有效，118/152 是**无意义的数** |
| 5 | 门禁上线**第一天全红 = 门禁活不过一周** | manifest 存量 14 处 version 漂移、8 处声明文件缺失 | 分档：破坏性的判 ERROR，其余判 WARN + 显式 backlog |
| 6 | **豁免是后门**，必须自带反向检查 | 删 `tests.entry` 是对的，但删了就静默了 | 登记豁免 + 写 reason + 写 reversal + 反向冲突检查（`EXEMPTION_CONFLICT`） |

## 一、先有分母，才有比率

### 错 1 — 拿着「104」这个数字直接开始分配

Phase-0 设计 v1.0 §6.1 写的是「从 **104 个**场景中分配 60/32/12」。
我核对仓库后发现，「场景」这个词至少指三样东西：

| 候选单位 | 数量 | 为什么不是它 |
|---|---|---|
| `.scenario.json` **文件数** | 37 | 一个文件可以是数组，含多个独立单元 |
| `driver.js` 全量回归的**单元数** | **123** | ← 本项目采用的口径 |
| 单测**断言数** | 216+ | 那是插件自己的单测，不是评估场景 |

37 → 123 的差异来源是实测出来的，不是推的：

```javascript
// eval/scenarios/driver.js 的 loadScenarios
const items = Array.isArray(parsed) ? parsed : [parsed];
for (const item of items) out.push({ file: f, scenario: substituteRoot(item) });
```

`agint-diagnosis.scenario.json` 一个文件 10 个单元，`agint-cron.scenario.json` 2 个。

> **规则**：设计文档里的**数字**和设计文档里的**名称**一样，都需要独立验证。
> 名字可以靠上下文猜，数字猜错就直接污染下游所有决策。
>
> 判据：当你准备说「X 占 Y 的 Z%」时，先问「**Y 的分母是怎么数出来的，代码在哪一行**」。
> 答不上来 ⇒ 这个百分比不许出现在交付物里。

⇒ 落地：`docs/eval/scenario-inventory.md` §2 定义单位的三条判定标准
（有唯一稳定 ID / 可独立判定 / 属于 92/104 计数），§2.1 列出全部 18 个多单元文件。

## 二、历史数字的两种读法

### 错 2 — 把「过时」当成「错误」

发现 92/104 与实测 123 差 19 之后，我的第一反应是：门禁跟文档对不上，
要么门禁算错了，要么文档写错了，得让它们一致。

如果按这个方向走，正确做法是「把 123 改回 104」或「把文档改成 123 了事」——**两种都错**。

git 逐级实测出的演变链：

| 时点 | 事件 | 单元数 |
|---|---|---|
| 2026-08-28 | v0.6.5 / Sprint 11 基线 | 104 |
| 08-29 | 新增 event-bus s12 | 110（+6） |
| 09-03 | 新增 self-model(10) + deploy-budget(5) | 125（+15） |
| 09-09 | 两个文件移入 `dedicated/` | 125（数不变，但**不再被 driver 扫到**） |
| **2026-10-02** | **driver 实测** | **123** |

结论：**92/104 在 2026-08-28 那个时点是完全准确的**，是货真价实的历史快照。
错的是 09-09 之后文档没跟着更新——**这是文档的债，不是门禁的 bug**。

> **规则**：看到「文档说 X、现在实测 Y」，第三种可能性必须先排除——
> **「X 在它自己的时点是对的」**。
>
> 查法固定：`git log --follow <文件>` + 在关键提交上 `git show <sha>:<file> | <计数器>`，
> 把数字的**时间序列**拉出来。拉不出序列，就没资格说哪个对。

同类的一个坑在 fail 数：文档称 12，实测 5，差 −7。**绝不能停在「部分已修复」**
——那是不及格的严谨度，因为它让 H1 配额的对象不明。必须逐项列出差集去了哪。

## 三、粒度必须对齐执行器

### 错 3 — 我按文件数记，runner 按单元数执行

Inventory 第一版把 dedicated 记成 **2 个单元**，`unitId` 全是 `( unnamed )`。
问题在于我用**文件枚举**做单位，而 dedicated 有自己的 runner：

| runner | 它自己的取数 | 单元数 |
|---|---|---|
| `run-mutator-eval.mjs` | `parsed.scenarios` | **19** |
| `run-counterfactual-stress.mjs` | `parsed.fixtures` | **10** |
| 合计 | | **29** |

于是「dedicated 有几个」这件事，从 2 变成 29——**而这个数决定了口径边界**。

> **规则**：一个执行单元的粒度 **由消费它的那个执行器定义，不由存储它的文件定义**。
> 问「执行器自己怎么数」，不要数文件。同理：driver 扫哪些文件以 driver 的
> `readdir` 为准，不以目录树存在什么为准。

## 四、分母纯净度：状态未知就别混进去

### 错 4 — 差点把 UNKNOWN 状态当成 0 fail 混进分母

dedicated 那 29 个单元，在 driver 口径下的 `lastKnownStatus` 是 `UNKNOWN`
——**没被执行过**，不是通过也不是失败。

如果按「总数 152」写通过率，会得到 `118/152 = 77.6%`。这个数字看起来正常，
实际上它把 29 个未知当成了 29 个非通过。**它比 78% 这个数本身更有害**，
因为它会让「dedicated 到底跑没跑过」这个问题永远消失在报表里。

⇒ 定案：dedicated 维持独立 runner，**不进任何分母、配额、通过率**。

| 口径 | 数值 | 有效性 |
|---|---|---|
| driver 口径 | **123** | ✅ 全部状态已知，118/123 可计算 |
| 按 runner 粒度并入 | 152 | ❌ 含 29 个 UNKNOWN，通过率不可计算 |
| 按 driver 历史口径 | 125 | ⚠️ 数字本身没错，但是**另一个口径**，不可与 123 混用 |

并把「反转条件」写死进 `unitScope` 字段（JSON 里的机器可读字段，不只是文档）：
runner 退役 → 并入 → **重跑全部配额计算**。

> **规则**：分母里只能放**状态已知的项**。`UNKNOWN` 不是 0，也不是 1，
> 它是「没测过」，混进任何比率都是造假。

## 五、门禁的第一天必须能过

### 错 5 — 门禁上线当天全红，然后所有人都会绕过它

`verify-manifests` 写完后实测：version 漂移 **14** 处、声明文件缺失 **8** 处、
`--strict` 下 **25** 处 WARN backlog。如果按「不一致就是错」的直觉全判 ERROR，
这道门禁**上线当天就红**。

红灯的门禁有两种结局：被人加 `--no-verify` 跳过，或被人往白名单里塞条目直到失去制衡。
两种结局都比没有这道门禁更糟。

⇒ 分档原则（可复用到任何新门禁）：

| 判据 | 级别 | 本轮实例 |
|---|---|---|
| 破坏性的（会导致运行时不正确） | **ERROR** | `name`/`main` 错、manifest 缺失 |
| 权威源尚未定义的（没有唯一真相可比） | **WARN** | version 漂移 16、声明文件缺失 |
| 门禁自身实现的问题 | **先修门禁** | `checkPlugin` name 比对用错字段 |

`MANIFEST_MISSING` 原本是误报（3 处），修完才升级 ERROR——**升级的前置条件是这一类已清零**。
清零前升级 = 制造新红灯。

### 附带：误报比漏报更该先修

`MANIFEST_MISSING` 旧实现对 `plugins/*` 做目录 glob，凡无 manifest 一律报警。
实测 3 处**全是误报**：`agint-quality` 是嵌套父容器（patch 挂的是它的子模块）、
`agint-search-tools` / `agint-session-extract` 在 `cordis.patch.yml` 里根本没挂载。

修法与 v0.9.0 的 4d 冒烟门禁同一思路：**集合来源从目录 glob 改为真实声明反查**
（读 `cordis.patch.yml` 的 `name: ./plugins/...` 行），并且正则**锚定行首**——
patch 里存在被注释掉的条目（`# - id: agint-quality-report`），不锚定会多算 1 条。

> **规则**：门禁报的每一条异常，先问「**这条是真的吗**」，再问「**怎么修**」。
> 误报清零之前不要谈严格化。以及：**未挂载的目录记为 notes，不静默吞掉**——
> 静默吞掉和误报一样有害，只是方向相反。

## 六、豁免是后门，得上锁

### 错 6 — 删掉假声明，事实也一起没了

`agint-quality-sdk` 的 `tests.entry` 指向一个不存在的文件。选项：
(a) 编个空测试文件骗过门禁；(b) 删声明；(c) 豁免。

选 (b) 是对的——**声明一个不存在的入口，比不声明更糟**，它会让「有 smoke 门禁」变成假的。

但删完就完事，等于让「这个插件没有测试」这个事实**静默消失**了。
后来补 README 时，同类问题在 memory/tool-stats 上又出现一次
（`tests.entry` 指向真实位置，但 README/CHANGELOG 缺失），说明这不是一次性问题。

⇒ 落地 `docs/manifest-declared-file-exemptions.json`，三条硬约束：

1. 每条必须写 `reason`（**为什么没有**）+ `reversal`（**什么条件下该恢复**）——
   没有 reason 的条目就是后门
2. **只豁免 `tests.entry`**。README/CHANGELOG 缺失一律补文档，不接受豁免
   （文档可以如实写出来，不存在编造问题；测试入口指向不存在的文件是欺骗）
3. **反向冲突检查**：豁免登记了、但文件真实存在 ⇒ 报 `EXEMPTION_CONFLICT`
   ——否则豁免会变成永久性的掩护

> **规则**：**豁免不是「承认现状」，是「把现状写下来并留反转条件」**。
> 一个没有 reason、没有 reversal、没有反向检查的豁免条目，
> 和把门禁删掉是同一个效果。

## 七、本轮还踩的两个小坑（记档备查）

1. **`classify()` 返回 `ALLOWLISTED` 不是 `ALLOWED`**。第一版测试断言写错，
   幸好自测抓到——**这正是「测试要钉返回值而不是钉自己记忆」的价值**。
2. **rebase 之后门禁转红是好事**。远程新引入的 `check-preset-parity.mjs` 用了
   `yaml`（宿主提供），本地零依赖门禁立刻报违规。**如果没在 push 前跑全量回归，
   这个红灯就被推上去了。** 先 `fetch` + 比两侧文件交集（为零）→ rebase → 重跑回归。
   详见 `docs/lessons/` 后续或 `check-soundness` §三。
