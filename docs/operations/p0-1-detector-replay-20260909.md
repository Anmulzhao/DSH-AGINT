### 3.2 「0 候选」的实测解释

- `skill-autocreate-aggregate` cron 挂 `45 4 * * *`，但 `cron_state` 里它的 `lastRunAt = 2026-09-08T00:39:51Z`——即 **autocreate 09-08 挂载后只跑过一次**
- 那次窗口内只有 **5 条记录 / 1 个任务实例** → 必然 0 产出
- DB 里 `task_patterns` 10 条全部 `occurrenceCount = 1`，与「只跑过一两次」完全吻合

> **真因：检测层还没正常跑起来，不是设计或参数问题。**

## 4. 结论三：真正的问题——可标准化过滤根本没实现

### 4.1 代码事实

- `detector.js:110-111`：`standardizable: null` / `standardizableConfidence: null`（**恒为空**）
- `proposer.js`：grep `diagnosis` / `annotate` / `standardizable` → **0 命中**
- 设计稿 §3.1 [4]「可标准化判断（调用 `agint-diagnosis`）」在代码中**不存在**

设计链路：`[3] 模式检测 → [4] 可标准化判断 → [5] 提案生成`
实际链路：`[3] 模式检测 → [5] 提案生成`（**[4] 被跳过**）

### 4.2 为什么这会出事

能跨过门槛的 7 个模式全是**极短、极通用的序列**：跑一次 PowerShell、写一条记忆、调一次技能。
这些**不是"可标准化的重复任务"**——给「跑一次 pwsh」建个技能是荒谬的。

设计稿靠 [4] 过滤它们：`rootCause ∈ {TOOL_GAP, KNOWLEDGE_GAP, PROMPT_DEFICIENCY}` 且 `confidence ≥ 0.6`。
**这道过滤不存在 → 检测层一出活，垃圾候选会直接灌进 Phase 1。**

### 4.3 顺带：这道过滤本身的准确率也没验过

设计稿 §14.2 列了待验证项「`agint-diagnosis` 的可标准化判断准确率：用 50 个已知可标准化/不可标准化的模式测试，Sprint 14」——**未做**。

## 5. 附带发现：tool-stats 采集疑似停摆

- `agint_tool_stats.jsonl` 最后修改 2026-09-08 22:50，最后一条记录时间戳 **2026-09-08T14:50:37Z**
- 核查时点 2026-09-09 12:04 → **近 22 小时零新记录**
- 日记录量也在衰减：2261(09-03) → 1698 → 727 → 526 → 151 → 5

需确认是「老板近期没在用 dsh」还是「tool-stats 写入链路断了」。若是后者，检测层无米下锅。
