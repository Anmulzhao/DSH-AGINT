# 设计稿 — agint-family-panel v2（从「手维护名册」到「派生视图」）

> 日期：2026-10-03　作者：智进
> 状态：**v2.1 修订版**（已并入评审意见，核心承诺已推翻重写）
> 评审原文：`proposals/agint-family-panel-v2-评审-20261003.md`
> 面板现版：v0.1.4（仓库 `plugins/agint-family-panel/` 与部署位 `~/.dsh/profiles/web/plugins/agint-family-panel/` 两份 `package.json` 同为 0.1.4；本稿取证读部署位）
> 老板起因原话：「现在的面板只是显示插件的激活状态，但是插件的产出及相互之间的关系和流程并没有体现……如何能更简单有效的获得系统的状态显得尤为重要」

### 版本历史

| 版本 | 结论 | 触发 |
|---|---|---|
| v1 | 「manifest 是零手维护的依赖真源」 | 初稿 |
| **v2.1** | **该承诺不成立。真源是插件源码，不是 manifest。** | 评审实测反证 + 源码扫描实测 |

---

## 0. 结论先行

**方向不变：删掉手维护的分组表，改成派生视图。**

**但 v1 的核心承诺错了，必须换掉。** v1 说「manifest 给出零手维护的依赖拓扑」。实测证明 manifest 里的依赖契约覆盖率不足 10%，照 v1 做会得到一张几乎空的图。

**修正后的结论：依赖拓扑的真源是插件源码，不是 manifest。**

理由是实测出来的密度差：

| 依赖信息来源 | 覆盖量 | 出处 |
|---|---|---|
| manifest `inject` 里的 `agint.*` 引用 | **10 条**，5 个插件 | 评审 §2.2 |
| manifest `consumes` 字段 | **3 / 34** 插件（8.8%） | 评审 §1、§4 |
| manifest `subscriptions` 非空 | **2 个**插件 | 评审 §2.3 |
| **源码 `ctx.get('agint.…')`** | **180 处命中**，约 28 个插件 | **本次实测** |

源码里的依赖密度是 manifest 声明的**一个数量级以上**。代码才是真契约，manifest 只是注释。

（180 是**上界**：grep 未剔除注释行。剔除后的准确数由步 0 测出。但它已经足以否定「manifest 能给出依赖图」这一条。）

**落地顺序改为四步**，新增的步 0 是评审建议，也是本次实测的直接产物：

| 步 | 做什么 | 阻塞关系 |
|---|---|---|
| **0** | manifest 普查 + 源码依赖扫描，产出两张基线表 | 独立 |
| 1 | 删 `FAMILY_GROUPS`，改三态判据 + 代码级依赖边 | 依赖步 0 |
| 2 | 加 L1 实测列（tool_stats / cron / event bus） | 前置：工具归属验证（U4） |
| 3 | 加 L2 判定层，声明 / 代码 / 实测三源对差 | 前置：步 2 归属可靠 |

本稿**不新增数据存储**。每个数字都要能追到系统已经在写的一份存储，或能从源码静态读出。

## 1. 评审推翻了什么

### 1.1 「零手维护拓扑」不成立

v1 的建边规则是「A 的 `provides` 与 B 的 `inject`/`optionalInject` 按服务名对上」。

实测（评审 §2.2）：34 个 manifest 的 `inject` 值里，`storageDomain` ×17、`tools` ×3、`webServer`、`timer`、`sandbox`、`agents` **全是宿主服务**；`agint.*` 家族服务引用只有 10 条。

**按 v1 规则只能建出约 10 条边，不是 40 节点关系图。**

三条退路都不成立：

- 接受稀疏 → 老板要的「关系」看不到。
- 补齐 31 个插件的 `consumes` → **这是新形式的手维护**，与删 `FAMILY_GROUPS` 的初衷相反。
- 运行时探测 `ctx.get`（评审建议）→ 能用，但要先在宿主侧加观测点，跨插件改动。

### 1.2 v2.1 的解：真源是源码

**直接在每个插件的源码里扫 `ctx.get('agint.…')`。**

这一步的性质要说清：它既不是 L0 声明，也不是 L1 运行时探测，而是第三种——**代码级真源**。

| 性质 | 说明 |
|---|---|
| 零手维护 | 代码改了，扫描结果自动跟着变。没有第二张表要维护 |
| 证据自带 | 每条边都带 `文件:行号`，L2 判据要的证据不用另外找 |
| 覆盖面 | 约 28 个插件 / 180 处命中，远超 manifest 的 3 个 / 10 条 |
| 成本 | 读每个插件的 `lib/*.js`，按 mtime 缓存，与 manifest 同一个缓存桶 |

**注释与代码必须分开统计**，这是 L2 判据的原料：

- 命中在可执行代码里 → 真依赖
- 命中只出现在 JSDoc / 注释里 → **文档腐化**：文档说了，代码没做

实证：本次 180 处命中里，注释命中肉眼可见，例如
`agint-metrics/lib/snapshotPublisher.js:8`（JSDoc）、
`agint-quality-static/lib/checkers/self-model-isolation.js:71`（检查器自己的说明注释）、
`agint-evolution-driver/lib/contract-manager.js:28`（JSDoc）。

准确比例待步 0 测。**这是本稿新增的核心判据来源。**

### 1.3 manifest 降级，但不下岗

manifest 仍然有价值，只是**不再承担建边职责**：

| 用途 | 字段 | 保留理由 |
|---|---|---|
| 节点属性 | `agint.owner` / `tier` / `kind` / `stability` | 代码里读不到 |
| 排期 | `mountOrder` | 代码里读不到 |
| 权限 | `permissions.env/fs/network/shell` | 代码里读不到（且是安全面） |
| 契约核对 | `provides` | 与代码扫描对差，查 manifest 漏写 |

⚠️ **解析器必须处理三种形态**（评审 §2.1 实测）：

1. **31 个**用 `spec.cordis` 包裹（evolution-driver 式）
2. **3 个**用顶层 `cordis`（`agint-abtest` / `agint-quality-sandbox` / `agint-quality-static`）
3. **3 个插件无 manifest**：`agint-quality`（聚合容器目录，子插件各有 manifest）、`agint-search-tools`、`agint-session-extract`

只按 evolution-driver 一个样本写解析器会漏 6 个插件。

### 1.4 一条建图硬约束：cordis 服务存储是扁平的

**多个插件在注释里反复记录同一个事实：`ctx.get('agint.eventBus')` 恒为 `undefined`，只有全名子键可用。**

证据（注释行，均为本次 grep 命中）：

- `agint-event-bus/lib/index.js:159`
- `agint-mutator/lib/index.js:1074`
- `agint-population/lib/index.js:550`
- `agint-diagnosis/lib/index.js:621`
- `agint-self-model/lib/index.js:417`
- `agint-evolution-memory/lib/index.js:705-711`

**影响**：建边时伞键（如 `agint.eventBus`）不可达。面板不能把它画成一条可用边，否则会画出一条「看起来存在、运行时恒 undefined」的假边。

这是一条**只读源码就能拿到、且不拿就会画错图**的约束。步 0 必须把它编码成建边规则。

### 1.5 补充证据：分组表自己也在漂移

评审 §3 建议 2 实测：`FAMILY_GROUPS` 有 **43 个成员名**，实机 **40 行**。

表上多出的 3 个名字，是 0.1.2 / 0.1.3 / 0.1.4 三次补表补进源码、但**对应的 loader 行并不存在**的名字。

**这是删表的最强补充证据**：这张表不仅漏（新插件进不来），还多（表里的名字对不上运行时）。

## 2. 修订后的四层模型

```
L0    属性层    manifest.json      → owner / tier / mountOrder / permissions
L0.5  代码层    插件源码            → 依赖边（真源，带文件:行号，区分代码/注释）
L1    实测层    已在写的存储 + 运行时 → 产出（调了多少、跑了几次、发了多少条）
L2    判定层    三源对差            → 异常（哪里在腐化）
```

### L0 属性层

三形态解析器，产出节点属性。读不到 manifest 的行进「无主插件」，**不静默丢弃**。

### L0.5 代码层（新增，建边的真源）

对每个家族插件扫 `lib/**/*.js`：

| 扫什么 | 产出什么 |
|---|---|
| `ctx.get('agint.…')` | 服务依赖边，标注 **代码** 或 **仅注释** |
| `ctx.provide('agint.…')` | 服务提供方，交叉核对 manifest 的 `provides` |
| `ctx.get('agint.eventBus.subscribe')` 等 | 事件订阅边（与 manifest `subscriptions` 对差） |
| 伞键形如 `ctx.get('agint.eventBus')` | **标为不可达**，不建边（§1.4） |

交叉核对用的现成样本：`agint-cron/lib/index.js:157-184` 是一张字面量服务表，一次列出 20+ 个 `agint.*` 服务，可作为扫描器的正确性基准。

### L1 实测层

| 源 | 取什么 | 归到哪个插件 |
|---|---|---|
| `agint.eventBus` | 每 topic 的发布数、投递数、deadletter、source | `deliveries` 点名了谁 |
| `agint_tool_stats.jsonl` | 每工具的调用数、失败率 | 见下方⚠️ |
| `agint.cron` | 任务数、上次跑、下次跑、从未跑过 | cron job 归属 |
| `agint.metrics` | 指标值 + delta | 指标 key 归属 |
| evolution ledger | commit / rollback 次数、改了什么 | `targetId` |

⚠️ **工具归属必须三源合并**（评审建议 4 + v1 的发现）：

- **源 A**：manifest 非空 `tools` 字段（评审实测 15 个插件有）
- **源 B**：preset 组合文件的 `agint-X-tools` 挂载行
- **源 C**：宿主 `tools` 服务实测（待 U4 验证）

**源 A 单独不可信**。反例（两边都读过）：

- `agint-abtest/manifest.json:19` 写 `"tools": []`
- 但 preset `agent.cordis.yml:387-388` 挂了一行 `agint-abtest-tools`，注释写「暴露 3 个工具」
- `agint-diagnosis/manifest.json:25` 同样为空，preset 里挂了 6 个
- `agint-wiki/manifest.json:17` 又老实列了 5 个 `wiki_*` 工具

**即：manifest 的 `tools` 字段时填时不填。**

**归属不全的工具归 host 内建，单列。** tool_stats 覆盖的是全量工具，`pwsh` 967 次 / `read` 516 次 / `grep` 379 次这些是宿主内建工具，**不能算到任何 agint 插件头上**。

⚠️ **延迟指标不进面板**。`tool_stats` 的 `avg` / `p95` 全部为 `0ms`，原因未查（U2）。查清之前展示它就是用恒零字段冒充测量。

### L2 判定层：三源对差

**这是 v2.1 相对评审建议的加强。** 评审建议 7 只要求补一条对称判据（声明无流量）。v2.1 把它扩成三源四象限：

| 代码里有 | manifest 声明 | 实测有流量 | 判定 |
|:---:|:---:|:---:|---|
| ✅ | ✅ | ✅ | **正常** |
| ✅ | ❌ | ✅ | **manifest 漏写**（依赖是真的，契约没跟上） |
| ✅ | ❌ | ❌ | **隐藏耦合**：代码在依赖，但没有流量。可能从未被触发，也可能是软失败 |
| ❌ | ✅ | — | **文档腐化**：manifest 声称的依赖，代码里根本没有 |
| 仅注释 | — | — | **从未接线**：文档写了，代码没做 |
| ✅ | ✅ | ❌ | **声明无流量**：两侧都声明了，运行时没用上 |

每条必须带证据（`文件:行号` + 实测计数），不允许只给结论。

**判据方向性**：最后两行合起来能判断架构腐化的方向——「声明无流量」偏空转，「文档腐化 / 从未接线」偏失真。

## 3. 面板形态

### Q1 — 服务依赖拓扑（主视图，事件链降为辅助）

评审建议 3 成立，v2.1 采纳并补上可行性：服务拓扑现在**可以**建出来了，因为真源换成源码扫描。

- **主视图**：服务依赖图。边 = 源码里真实的 `ctx.get('agint.*')`。
- **辅助**：事件链**只显示有 `deliveries` 的 topic**（当前 1 条）。
- **另标注**：「已订阅但从未收到消息」的关系。
- ⛔ **不画力导向图**（见 §5）。

事件订阅的实时查询需要 event-bus 补一个只读出口（评审建议 3.3：订阅表当前是模块级 Map，重启即重建，无查询接口）。**这是跨插件改动，不在步 1 范围内。**

### Q2 — 谁真的在干活

表格：`插件 | 工具调用 | 失败率 | cron 次数 | bus 发布 | 最近活动`。

**0 产出的行自动沉底。** 这一步替掉「40 个一样绿的点」——绿点不携带信息，排序携带。

### Q3 — 哪里在腐化

L2 异常清单，每条带证据。

**只读导出出口**（评审建议 8，老板拍板方向）：Q3 可导出为 evolve 提案草稿（Markdown / JSON），老板一键确认后再提交。⛔ 不自动喂 `evolve.propose`，不破坏只读不变量。

## 4. 四条纪律

| # | 纪律 | 理由 |
|---|---|---|
| D1 | **不自造第二份真相。** 每个像素都要能追到系统已在写的一份存储，或能从源码静态读出 | 面板一旦自己存，就会跟着一起腐烂。这就是 `FAMILY_GROUPS` 的死法 |
| D2 | **宿主聚合，浏览器只渲染。** 保持现有 `buildStatus` 形状 | 浏览器里聚 6 个源会得到撕裂快照 |
| D3 | **快照要带龄期。** 每个源带 `observedAt`，面板显示「指标 3 分钟前」 | 多源聚合必然时间不一致。现状只有单个 `generatedAt`（`index.js:345`） |
| D4 | **宿主侧缓存 + mtime 失效。** TTL 30 秒，**并**记录 manifest / 源码的 mtime 与 version，变了立即重读（评审建议 6） | 30 秒 TTL 单独不够：插件更新后面板会显示旧图 30 秒。可接受，但要有 `observedAt` 标注 |

**降级分级照抄现有的好设计**：`probeSignal`（`index.js:258-279`）已做到「单源挂 → 该信号 `unavailable` + reason，其余照常」，且 `unknown` 是琥珀色不是绿色。扩展到 L1 全部源即可，不要重新发明。

### 面板自身健康信号（评审建议 9）

面板现在是家族的可观测面。它自己不可观测，本身就是盲区。补三条：

1. manifest 解析失败数（按三形态分别计）
2. 缓存命中率
3. 各数据源 `observedAt` 覆盖率

## 5. 反模式

| ⛔ 别做 | 为什么 |
|---|---|
| **画力导向图** | 40 节点、自变结构、每次刷新重排。没人能从一团线里读出信息。用表格 + 邻接表 |
| **把伞键画成可用边** | cordis 服务存储是扁平的，`ctx.get('agint.eventBus')` 恒 undefined（§1.4） |
| **给面板加写路径** | 只读。一旦能写，它就参与决策，第二真相源成立 |
| **手画流程图** | 手画的图第一次就过期。必须由实测 `deliveries` 得出 |
| **保留 10 组静态分组** | 那正是要删的东西。分组若要保留，必须由 `agint.tier` / `mountOrder` 派生 |
| **用 manifest `tools` 做工具归属** | §2 已证：时填时不填 |
| **用 manifest `consumes` / `subscriptions` 建边** | 覆盖率 3/34 与 2 个插件 |
| **展示延迟指标** | U2 未查清，avg/p95 恒 0ms |
| **把宿主内建工具算进 agint 产出** | `pwsh` / `read` / `grep` 不属于任何 agint 插件 |

## 6. 落地顺序

### 步 0：普查（评审建议 0，新增）

**做什么**：

1. **manifest 普查表**：34 个 manifest 的形态分类 + 字段覆盖率。本稿已有主体数据（评审 §2.1、§2.3）。
2. **源码依赖扫描基线**：每个插件 `lib/**/*.js` 里 `ctx.get('agint.*')` / `ctx.provide('agint.*')` 的命中数，**区分代码与注释**。补齐 180 这个上界的准确数。
3. **交叉核对**：源码扫出的依赖 vs manifest 声明 vs `consumes`，产出一张「差异基线表」。
4. 把三张表写进 `test/smoke.mjs` 的 fixture，成为回归基线。

**产出**：两张基线表 + 一个差异表。**这一步不改任何生产代码。**

**为什么先做**：步 1 的解析器和建边规则完全依赖这几张表的数字。先写代码后测数，等于拿猜测当设计。

### 步 1：删 `FAMILY_GROUPS`

**改动面**：`lib/index.js`（`splitFamily` + `groupFamily` + `buildStatus`）、`lib/client.js`、`test/smoke.mjs`。

**做什么**：

1. 三形态 manifest 解析器（§1.3）。
2. **判据三态化**（评审建议 1，修 v1 的双报矛盾）：

   | 态 | 判据 | v1 的问题 |
   |---|---|---|
   | **正式成员** | manifest 存在且含 `agint` 段 | — |
   | **显式成员** | `EXTERNAL_FAMILY_MEMBERS` 兜底名单命中（`dsh-kill-switch`） | v1 会把它同时报成「家族成员」和「无主插件」，**双报矛盾** |
   | **无主插件** | 挂载 + 无 manifest + 不在兜底名单 | — |

3. 依赖边改为源码扫描（§1.2），伞键不建边（§1.4）。
4. 删 `FAMILY_GROUPS`。分组信息降为按 `agint.tier` / `mountOrder` 派生。
5. 缓存加 mtime 失效（D4）。

**验收口径重定义**（评审建议 2）。v1 说「`counts.total` 与 40 对齐」——**这条作废**，因为新判据下 3 个无 manifest 插件掉出正式家族。

改为三项断言：

| 断言 | 期望值 |
|---|---|
| 正式成员数 | 步 0 普查表的实测值（**待填**） |
| 无主清单 | `{agint-quality, agint-search-tools, agint-session-extract}` |
| 兜底行 | `{dsh-kill-switch}` |
| `hostRowCount` | 239 不变（沿用 CHANGELOG:64-66 口径） |

### 步 2：加 L1 实测列

**硬前置**：U4 验证。评审建议 5 已把可行性的地板抬高——`ctx.tools` 确认是合法注入名（`tools.register()` / `tools.get(name)` 存在，memory-provider `manager.js:1239`），**但「枚举全部注册工具」与「注册者归属」两个 API 尚未确认**。

- 若 host 暴露枚举 + 归属 → 三源合并可自动化
- 若只有 `get(name)` → 归属退到「命名前缀 + preset 挂载行」，且 **L2 的「隐藏耦合」判据降级为「无法归属时标 `unknown`」**

**顺带补 L1 的取舍**：`tool_stats` 里 `edit` 失败率 13.1%、`skill` 失败率 25.8%——这两条本身就值得在 Q2 标红，不需要额外数据源。

### 步 3：加 L2 判定层

**前置**：步 2 的归属映射必须可靠，否则「隐藏耦合」「僵尸插件」两条判据会给出错误结论。

**做什么**：Q3 异常清单，按 §2 的三源四象限 + 两条单源判据。每条带证据。加只读导出出口。
